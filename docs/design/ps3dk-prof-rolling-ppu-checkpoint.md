# Offline PPU checkpoint slice

Status: internal offline semantic work toward rolling capture. This is not an
enabled SDK capture mode. It is independent of the physical store described in
[ps3dk-prof-rolling-store.md](ps3dk-prof-rolling-store.md); neither component
currently connects the runtime sink, reader file dispatch, CLI, viewer, or live
protocol to rolling capture. The complete rolling-capture task remains open.

The Rust `ps3dk_prof::rolling` module exposes two operations:

* `checkpoint_ppu(prefix, limits)` accepts an original 16-byte file header and
  a whole original chunk prefix, without TRAILER. It returns a typed checkpoint.
* `read_ppu_suffix(checkpoint, suffix, limits)` accepts that checkpoint and
  original framed chunks starting at its exact next chunk sequence. It returns
  `RetainedPpu`, not a legacy full-capture `Analysis`.

Only PPU records and optional WINDOWS are supported: original file flags must
be zero or `FLAG_WINDOWS`. Other families, including SPU, ORDER, GPU, AUTO, FIFO,
WAIT, FUNC, COUNTERS and export metadata, are explicitly refused. This profile
also requires increasing BEGIN span IDs per incarnation, as generated by the
runtime. That restriction permits a bounded high-water value instead of the
legacy reader's unbounded set of historical IDs. Legacy v1 acceptance is
unchanged.

## State and validation

The checkpoint stores the actual original file header and original non-event
chunks with their original sequences and CRCs. Those metadata chunks are
validated individually by the existing header, clocks, descriptor, thread,
retirement and window validators. They are not assembled into a fabricated v1
prefix. All closed window metadata is retained for strict sequencing, although
closed prefix windows are omitted from retained-window presentation.

Sequenced event history is compacted to per-incarnation counters/cursors,
active BEGIN/BEGIN_PARENT stack entries, a maximum span ID, exact recorded
frame-membership runs, and unresolved token references. Closed evicted zones
are not replayed. Unresolved tokens from closed prefix zones remain subject to
token rule 4, even though those zones are absent from retained results.

The same core record and final-entry validators process the suffix. The final
equations are:

```text
written_final = written_prefix + written_retained
produced_final = written_final + dropped_final
dropped_final = gaps_prefix + gaps_retained + produced_final - next_sequence
regerr_final >= regerr_prefix + regerr_retained
written_prefix + gaps_prefix = next_sequence_at_cut
```

All applicable original state-3, counter-range, limit-flag, retired-entry and
trailer rules remain active. A genuine GAP remains producer loss; eviction
does not synthesize GAPs. Prefix frame-skip permission and unknown stack base
require actual prefix loss. Exact frame IDs satisfy the original
`frame_id <= sequence < 2^63` rule, so u64 frame-ID exhaustion is unreachable.

Prefix counters additionally conserve original framing:

```text
prefix_bytes = original_metadata_chunk_bytes
             + 28 * original_RECORDS_chunk_count
             + 32 * (sum_prefix_written + sum_prefix_GAP_rows)
```

`prefix_bytes` excludes the 16-byte file header. A RECORDS chunk has 20 framing
bytes, 8 payload-header bytes, and 32 bytes per sequenced record or GAP row.
This equation is checked even when the suffix has no TRAILER. CRCs detect
corruption; they do not authenticate producer claims or recover evicted bytes.

Active prefix spans validate retained END identities and stack topology. Their
durations are left-censored and never counted as complete retained work.
Complete retained children remain independently measurable under ordinary
loss, refusal, clock and final-state conditions. Output includes the original
chunk interval, prefix byte count, separate prefix/retained lane counts, and
explicit window clipping. Torn suffix tails remain `TornTail`/`NoTrailer`;
checkpoint creation refuses torn prefixes and prefixes containing TRAILER.

## Bounds and wire schema

`Limits` is caller policy. Defaults are 8 MiB checkpoint bytes, 4 MiB bootstrap
metadata bytes, 4096 incarnations, 4096 descriptors, 65536 combined frame runs
and unresolved token identities, 262144 active stack rows, and one million
input record rows per operation. Per-lane stacks cannot exceed 256 rows.
Exhaustion returns an error; it does not waive a validation rule.

Original chunk payloads retain the existing 1 MiB cap. Before collecting a
RECORDS chunk, the scanner requires positive `n` and exact payload length
`8 + 32*n`, then charges `n` against `work_records`. Thus accepted RECORDS
chunk count is at most `work_records`, and their total framed bytes are at
most `60 * work_records`. Other framed chunk bytes are charged to
`metadata_bytes`, whose scanner accounting starts at 16 bytes. The scanner
does not copy record payloads. It still inventories chunks, and the shared
reader temporarily holds input spans; this offline operation is not the
eventual bounded-memory incremental runtime checkpoint generator.

Checkpoint decoding checks byte/count limits before variable-row allocation.
The shared metadata reader may allocate up to one capped chunk before the
descriptor/incarnation policy check. Existing Rust collection allocations
are not a guarantee of recoverable process-wide allocator exhaustion.

Schema 1 uses little-endian fields, magic `PFRCKP01`, a 64-byte fixed header,
three canonical sections with 16-byte envelopes, and a trailing IEEE CRC32.
The sections are original bootstrap metadata, lane restart rows, and pending
token identities. Reserved fields must be zero; unknown, duplicate or
out-of-order sections and mismatched lengths/counts are refused. Lane rows
have a 120-byte fixed portion, 80 bytes per active stack row, and 16 bytes per
frame-membership run. Pending token identities occupy 16 bytes each.

## Remaining integration

The next semantic work must preserve SPU brackets and ORDER evidence, manual
GPU calibration, AUTO anchors/publication state and FIFO accounting, including
cross-window references. Each family needs bounded serialized restart state,
exact prefix-plus-retained equations and independent negative controls.
Unsupported flags cannot simply be removed from production captures to make
this PPU slice appear usable.

After those semantics are verified, a runtime encoder must create compatible
checkpoints incrementally and connect whole chunks to the physical store,
with explicit metadata-cap refusal. Reader dispatch, retained-window analysis,
live generation/resnapshot negotiation and runtime rotation tests remain.
Completed-capture retention is a separate policy from this checkpoint format.
