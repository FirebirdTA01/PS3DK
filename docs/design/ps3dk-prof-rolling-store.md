# Profiler rolling store: internal physical foundation

Status: **internal storage foundation, not an enabled profiler or SDK feature**.
`sdk/libps3dkprof/src/rolling/roll_store.{h,c}` is standalone portable C11 code.
It is not connected to the timing sink, installed as a public API, enabled by a
runtime option, or supported by the live profiler protocol. The ordinary
append-only capture path is unchanged.

The complete rolling-capture task remains open. This component supplies a
bounded physical container and opaque checkpoint storage. It does **not** prove
that a checkpoint can restart the PPU, SPU, RSX, or any other record-family
reader. It does not implement completed-capture retention.

The Rust `ps3dk_prof::rolling_store::read(bytes, limits)` reader validates this
physical format independently. It takes an immutable, coherent byte snapshot,
enforces caller file/slot budgets, and chooses one fully validated root chain.
It borrows checkpoint and payload slices and allocates at most two vectors of
64 segment descriptors. Configuration and session identity come from the
validated configuration page; callers needing an expected external identity
must compare that identity themselves. Checksums do not authenticate a file.
Recovery status is explicit, and unused slots are never scanned to reconstruct
an uncommitted history. This API does not provide live-file snapshot retries,
semantic checkpoint validation, CLI dispatch, or runtime integration.

Rust controls cover corrupt roots, slots, footer and chunk framing, repaired
outer checksums, identity/range errors and admission budgets. CI also explicitly
runs the C-artifact parity test against `rotated.profr` generated by the C writer;
that test refuses a missing artifact instead of silently skipping it.

## Storage contract

The owner supplies an exclusive file adapter, aligned state storage, and a
scratch buffer. The component allocates no memory, takes no locks, performs no
OS calls directly, and changes no producer state. All operations on a handle
must be serialized by its owner.

The configuration specifies a maximum logical file size, 2–64 retained segment
slots, a checkpoint byte budget, a payload byte budget, and a 16-byte capture
identity. There is one additional spare slot. Format requires an initially
zero-length file; it refuses to replace a populated file.

For checkpoint capacity `C`, payload capacity `D`, and retained slot count `N`:

```text
slot_bytes = align_up(96 + C + D + 64, 4096)
file_bytes = 12288 + (N + 1) * slot_bytes
file_bytes <= configured_max_bytes
```

The cap includes the immutable configuration page, both roots, every slot,
spare space, and padding. Filesystem allocation-unit overhead is outside this
logical byte count. Resizing a file does not promise physical disk-space
reservation. Overflow or insufficient space is refused rather than rounded
beyond the requested maximum.

Payload consists of complete original v1 chunks, each with its 16-byte chunk
header and 4-byte IEEE CRC32. Chunk payload length is limited to 1,048,576
bytes. Original chunk sequences begin at zero and remain contiguous; the
physical layer verifies framing, CRCs, sequence continuity, and overflow. It
does not interpret chunk types or payload semantics. The separate 16-byte v1
file header is **not** a chunk and cannot be put into this payload directly.
The eventual semantic checkpoint format must retain it and the appropriate
HEADER/CLOCKS/PROFILE state.

A metadata-only segment with an empty payload is allowed. A small physical
payload budget is useful for tests; runtime integration must either reserve
room for the largest emitted chunk or explicitly reduce encoder chunk limits.
It must never split a chunk across segments.

## Internal API

Names in the private header are aliases for `ps3dk_prof__roll_*` symbols.

| Operation | Contract |
|---|---|
| `pfr_plan` | Checks the configuration and returns exact logical length, slot size, and required scratch bytes. |
| `pfr_state_bytes` | Returns opaque state allocation size; use malloc/max_align_t alignment. |
| `pfr_format` | Creates configuration and the initial committed empty root in an exclusive zero-length file. |
| `pfr_open` | Requires matching configuration/session, validates both complete root chains, and selects the newest valid one. A read-only adapter is allowed. |
| `pfr_commit` | Writes a bounded opaque checkpoint and whole-chunk payload as one new segment; evicts the oldest segment only through root publication. |
| `pfr_get_view` | Returns committed generation, retained original chunk/segment ranges, and cumulative evicted segment/chunk/payload-byte counts. |
| `pfr_get_segment` | Validates and reads a retained segment by oldest-first index. Returned byte pointers borrow caller scratch until the next operation. |

State, scratch, and commit inputs must not overlap. The adapter uses explicit
64-bit offsets and provides `read_at`, `write_at`, `size`, `resize`, and `sync`.
Positive short reads/writes are retried; zero, negative, or overlarge transfer
counts fail. The adapter owns EINTR handling. Read-only opens may omit write,
resize, and sync callbacks; commits then fail explicitly.

Invalid payload/capacity arguments are refused before IO. Any commit IO failure
poisons that handle: subsequent operations cannot claim an authoritative
committed view or continue writing. Reopen under exclusive ownership to learn
which generation is recoverable. A failed final sync may leave either the old
or the new complete root visible under the adapter's failure model.

## Container layout

This is a development format. Its physical version does not define a stable,
released semantic restart format. All integers are little endian and encoded
explicitly; disk bytes are never cast to C structures. Reserved bytes and
padding must be zero.

| Offset | Content |
|---|---|
| 0 | 4096-byte `PS3DKROL` configuration page, version 1. |
| 4096 | Root page for even generations. |
| 8192 | Root page for odd generations. |
| 12288 | `N + 1` equal-sized segment slots. |

The configuration page binds logical length, cap, capacities, slot count/size,
session identity, and a CRC at byte 4092. The root page has `PFRROOT1` magic,
generation, retained count, original frontiers, cumulative eviction counts,
session identity, and 40-byte slot entries beginning at byte 96. Each entry
contains physical slot index, actual checkpoint/payload lengths, segment
sequence, and original first/next chunk sequences. A root CRC occupies byte
4092. The initial root is generation 1 with no segments; segment zero is
committed by generation 2.

Each slot has a 96-byte `PFRSLOT1` header, actual checkpoint bytes, actual payload
bytes, zero padding, and a 64-byte `PFRCMIT1` footer. Header/footer bind the
session, segment/generation, original chunk range, lengths, and checksums. The
footer also checksums the full preceding slot content, including padding.
Exact field offsets are documented beside the encoder in `roll_store.c` and
decoded independently by the host test oracle.

Checksums detect inconsistent/torn content. They are not authentication or
independent evidence for the contents of an evicted prefix.

## Commit and recovery

For each commit:

1. Choose a slot absent from the current valid root, before removing any entry.
2. Write the complete new slot and call the adapter's sync operation.
3. Write the alternate root, adding the new segment and removing the oldest
   entry if the retained set is full; sync again.
4. Publish the new in-memory committed root only after both stages succeed.

The current root is not invalidated before the spare write. The older root may
reference that spare slot and cease to be usable during the next transaction;
recovery does not assume that both historical roots remain valid.

Open checks file length/configuration, each root, all its referenced slot
identities/generations/checksums, and every original chunk. It selects the
highest generation whose **entire** chain validates. Falling back or observing
a damaged alternate root is exposed through the recovered indicator. With no
complete valid root, the operation returns corruption; it never combines
surviving segments from incompatible roots or skips a corrupt interior chunk.

The adapter must establish ordering of completed syncs relative to later
writes. This interface and checksum protocol alone do not establish a
filesystem/device power-loss guarantee or assume any atomic sector size.
Target filesystem sync/resize behavior still needs hardware validation.

The private `roll_file` adapter borrows an exclusively owned read/write file
descriptor. Its caller serializes access and remains responsible for opening
and closing it. Host calls use 64-bit positioned IO; LV2 uses the explicit
64-bit seek, read/write count, file-size and resize interfaces in both PPU
ABIs. LV2 access can move the descriptor cursor. Every request is checked
against a fixed extent, at most `INT64_MAX`, before any IO. Each transfer is
limited to `INT_MAX` bytes; a positive short result is returned to the store,
while an interrupted call fails without retry. Resize success requires a
subsequent exact size check. Sparse resizing does not reserve disk capacity.
The adapter is not yet connected to runtime capture admission.

Opening or reading segments while another owner overwrites slots is not an
atomic live snapshot. Individual reads revalidate their slot identities and
checksums, but a generation-aware copy/retry protocol is required for a coherent
live capture. The existing ever-growing DATA-offset protocol is not compatible
with this circular file layout.

## Test scope

The standalone harness lives in `tests/host/ps3dk-prof-rolling/`. It does not
link the SDK runtime or use hardware. Run in an explicitly selected build
directory:

```sh
python3 tests/host/ps3dk-prof-rolling/run.py --build-dir /path/to/local/build
python3 tests/host/ps3dk-prof-rolling/mutations.py --build-dir /path/to/local/mutations
python3 tests/host/ps3dk-prof-rolling/run_file.py --build-dir /path/to/local/file
python3 tests/host/ps3dk-prof-rolling/run_file.py --lv2-mock --build-dir /path/to/local/file-lv2
python3 tests/host/ps3dk-prof-rolling/file_mutations.py --build-dir /path/to/local/file-mutants
```

`--cc` selects a C11 compiler command. The normal runner compiles the real store,
runs the memory-adapter tests, and independently decodes a C-produced container
using Python `struct` and `zlib`. `decode.py --self-test` exercises only the
decoder controls, not the C implementation. The separate `--red` runner mode
uses an explicitly test-only missing-feature stand-in for the recorded initial
test-first failure; it is never linked into production.

Tests cover twelve commits with three retained slots, oldest eviction and
newest data, exact cap arithmetic, positive short writes, invalid/torn chunk
input, failures at each format/commit IO stage, poisoned handles, corrupt
configuration/roots/slots/checkpoints/payload, and complete-chain fallback.
Fault adapters model both immediately visible writes and volatile writes
discarded before a successful sync. These models are not target filesystem
measurements.

Seven targeted mutation controls remove spare accounting, overwrite the
current oldest slot, accept bad chunk CRCs, ignore slot integrity, accept an
incomplete root chain, keep writing after IO failure, or omit the slot-sync
barrier. The mutation runner requires a passing baseline and rejects compiler
errors as harness failures rather than counting them as killed mutations.

Positioned-file tests use an actual sparse host file above 4 GiB, short writes,
an interrupted transaction, poisoned-handle refusal and reopening the previous
committed root. The LV2 test models syscall return shapes, including a wrong
seek position and an impossible returned count; it does not exercise a PS3
filesystem. Six mutation controls require assertion failures for offset
narrowing, missing extent checks, unchecked resize, unchecked seek position
and unchecked transfer count. Both PPU ABIs also compile the store and adapter
with warnings treated as errors. These checks do not establish console IO
behavior or power-loss durability.

## Work required before enabling rolling captures

The complete feature still requires:

* A bounded semantic checkpoint schema and accepted-output state mirror for
  every enabled record family, preserving exact final conservation equations.
  Eviction is distinct from producer GAP/LOSS; EXPORT40 is not a generic suffix
  proof.
* Real HEADER/CLOCKS/PROFILE, dictionary/incarnation, active-stack, frame/window,
  calibration, and SPU order support. Retained interior SPU/RSX measurements must
  remain useful; missing boundary evidence must be explicitly censored.
* AUTO and its mandatory FIFO provider, including type43 FIFO accounting,
  cumulative status validation, clock qualification, and incomplete boundary
  frames. WAIT/FUNC/COUNTERS/frame-evidence support or explicit initialization
  rejection is necessary for configurations advertising those capabilities.
* Runtime option/ABI work, preallocation/resource limits, a drainer-owned
  accepted/committed frontier, FILE adapter integration, initial metadata
  publication, and correct shutdown/quick-exit behavior.
* A terminal/resource-stop representation, checkpoint import and analysis in
  the PC reader/viewer, coherent live snapshot negotiation, and completed-file
  retention as its own lifecycle policy.
* Cross-family corruption tests and measurements of checkpoint size, memory,
  sync latency, and sustained rotation cost. The present codec writes a full
  padded slot per commit; a large checkpoint at ordinary drain cadence can be
  expensive.

Until that work is complete, this foundation must not be presented as an
available maximum-capture-bytes option or as completion of the rolling-capture
task.
